# BobTools Handoff — 2026-03-15

> Later update: this handoff predates the canonical `live-results.json` store, the review-driven scan batch export flow, and the matching mining review workflow. Use it as historical architecture context, but prefer `CURRENT_STATE.md` for current behavior.

## Project intent

BobTools is a Windows WPF overlay app for capturing a selected region from the visible Star Citizen game window, running OCR on that region, and helping the user review and classify the result.

The app is intentionally screen-based, not memory-based:

- it captures desktop pixels from the Star Citizen client area
- it does not inspect game memory
- it is designed around borderless/window-visible capture reliability

## Major evolution so far

### 1. Core capture + OCR baseline

Initial app behavior captured a selected screen region and ran Tesseract OCR over the image.

Why this path was kept:

- it is simple and legal from an application boundary perspective
- it avoids game-process memory inspection
- it is easy to debug visually using saved images

### 2. Hotkey and selection reliability

The hotkey was changed to `Alt+B`, and the app was updated to stop hardcoding hotkey behavior in the window layer.

Selection flow was also fixed so the capture region can be reselected reliably after prior captures.

Why this path was chosen:

- settings-driven behavior is easier to maintain than window-level hardcoding
- selection bugs were usability blockers, so they were fixed near the root flow instead of patched around

### 3. Star Citizen-only capture scope

Capture was restricted to the visible `StarCitizen.exe` window/client area.

Why this path was chosen:

- OCR quality suffers badly when unrelated desktop content is included
- user intent is explicitly game-only
- monitor/window clamping prevents oversized multi-monitor selections

### 4. Overlay windows and DPI correctness

The app gained:

- a transparent highlight overlay for the selected region
- a compact top-of-screen translucent UI
- DPI conversion fixes between WPF device-independent units and physical capture pixels

Why this path was chosen:

- visual feedback makes region setup much easier
- DPI mismatch was causing real capture errors, not just cosmetic drift
- a compact overlay is more practical during gameplay than a normal window

### 5. OCR tuning and offline workflow

The OCR pipeline was expanded significantly:

- image upscaling
- grayscale conversion
- contrast stretching
- multiple Otsu threshold variants
- multiple Tesseract page segmentation modes
- manual OCR mode selection
- debug artifact saving
- replay CSV generation for offline comparisons
- offline image testing inside the app

Why this path was chosen:

- OCR problems were data-dependent, not solvable with one global threshold
- saved debug images make failures explainable
- offline replay is much faster than testing only in-game

### 6. Dual capture profiles

Two capture profiles were added:

- `Signature`
- `Mining`

Each has its own saved region and can be used independently.

Why this path was chosen:

- the OCR targets are different enough to justify separate regions and workflows
- this avoids constantly resetting a single region

### 7. Signature icon-guided extraction

Signature handling now has a specialized path.

When Signature is selected and OCR mode is `Auto` or `Rightmost Numeric Value`, the app first tries to:

- find the signature icon using template matching against `Assets/images/signature_icon.png`
- crop candidate regions to the right of that icon
- OCR only those numeric regions with a numeric character whitelist
- prefer results that look like real signature values such as `4,000`

The implementation evolved in several steps:

- initial icon matching
- transparency-aware matching using the PNG alpha mask
- wider and adaptive template scale search
- multiple nearby crop regions instead of a single crop guess
- stronger ranking for comma-formatted multi-digit numbers
- grouping/voting across repeated candidate values

Why this path was chosen:

- generic OCR could read nearby UI noise better than the actual signature number
- the signature UI has a stable icon anchor, so anchor-based OCR is more robust than full-region OCR
- live captures had scale differences vs sample images, so adaptive scale search was necessary

### 8. Signature-to-resource lookup

The app now maps Signature OCR results to resources using `Assets/data/signatures.csv`.

Lookup rule:

- parse the OCR numeric value
- find CSV rows where `ocrValue % signatureValue == 0`
- prefer an exact match
- otherwise prefer the largest matching divisor

Example outputs:

- `Signature resource: Ground-Veh (4,000)`
- `Signature resource: Salvage (2,000 × 2)`

Why this path was chosen:

- the user stated the OCR signature value is a multiple of a known base signature from the CSV
- divisor-based matching is more flexible than exact-only lookup

## Current UX behavior

### Live Signature capture

When `Signature` is captured live:

1. the saved Signature region is captured from the Star Citizen client area
2. OCR runs, with icon-guided extraction attempted first when eligible
3. the live results tab updates with:
   - extracted OCR text
   - OCR mode actually used
   - OCR source summary
   - matched signature resource
4. the review dialog opens and shows the matched resource above the editable OCR text

### Offline Signature testing

When an offline image is dropped and Signature is selected:

1. if the saved region fits, that region is used
2. otherwise the whole dropped image is used
3. OCR runs
4. the offline results panel shows:
   - OCR text
   - matched signature resource
   - preview selection mode

### Mining behavior

Mining continues to use the general OCR flow. Signature-specific resource mapping is intentionally not applied to Mining.

## Important design decisions

### Keep screen OCR, not memory reading

Chosen because the tool is meant to operate on visible game UI safely and transparently.

### Special-case Signature rather than overfitting all OCR

Chosen because the Signature UI has a stable icon and known numeric semantics, while Mining can keep using the broader OCR pipeline.

### Prefer debug artifacts over hidden heuristics

Chosen because OCR tuning is much easier when every failure leaves behind:

- source capture
- processed images
- icon-match summary
- OCR attempt summaries

### Prefer additive improvements over risky rewrites

Chosen because the app has grown incrementally around real user feedback. Most changes were targeted to the active pain point without destabilizing unrelated workflows.

## Current known strengths

- reliable Star Citizen-only capture
- good overlay/selection UX
- offline OCR tuning workflow is strong
- Signature icon-guided OCR is materially better than generic OCR alone
- resource lookup is now visible in both live and offline paths
- Mining exports now produce structured CSV/JSON artifacts with parse warnings and a session-scoped identifier

## Current known limitations / likely future work

- Signature icon matching still depends on image quality and may need further tuning for new UI scales or lighting conditions
- review-time resource display currently uses the pre-accept OCR result, not any edited text after acceptance
- Mining does not yet have an equivalent domain-specific post-processing layer
- there is not yet a dedicated "latest debug capture" shortcut in the UI
- replay CSV currently focuses on OCR outputs, not resource-match correctness
- Mining `COMPOSITION` depends on OCR surfacing that scalar value explicitly; it is not inferred when absent
- Mining element rows may still be partial when OCR loses percentages or qualities, though those cases are now preserved with `PARSE_WARNINGS`

## Mining export contract

The mining export format has been aligned to `Assets/data/SampleRock.json`.

Important details:

- `SESSIONID` is generated once at app startup and reused until the process closes
- `MASS`, `RESISTANCE`, `INSTABILITY`, and `COMPOSITION` are exported as numeric values, not strings
- `Elements` is the per-material array
- `PARSE_WARNINGS` captures OCR/parser fallbacks such as reconstructed mass or missing element percentages
- JSON is written into the matching debug capture folder when one exists, which makes review of source images and structured output much easier

## Practical debugging notes

If Signature OCR regresses again:

- enable `Save debug`
- inspect the newest debug folder under `LocalAppData/BobTools/DebugCaptures`
- pay special attention to:
  - `01_capture.png`
  - `00_signature_value_region.png`
  - `00_signature_icon_match.txt`
  - `ocr_attempts.txt`

Those files usually tell whether the failure is:

- wrong icon scale
- wrong crop placement
- OCR preprocessing
- value ranking / selection

## Summary

The project has moved from a generic OCR capture overlay into a more domain-aware Star Citizen helper.

The biggest successful pattern so far has been:

- constrain the capture target tightly
- save rich debug artifacts
- add domain-specific post-processing only where the UI pattern is stable

That is the same reasoning behind the current Signature icon-guided OCR path and the CSV-based resource lookup.
